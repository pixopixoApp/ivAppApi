# 视频推荐算法方案说明

## 一、背景与目标

当前视频推荐在一次下拉中需要稳定、高质量地返回一批视频，同时满足**去重、分层、刷新、兜底**等要求。本方案基于 Redis 内容池 + 5 档位分层采样 + 体验曲线编排实现，做到：

- **稳定出量**：每次下拉固定返回 20 条
- **质量分层**：视频按质量分 5 个档位，按“橄榄型”供给（中间档为主、高档精品保量、低档少量）
- **体验排序**：最终 20 条按“体验曲线模板”编排（高质开场、主体承接、避免单调递减、收尾钩子），而非简单随机或单调降序
- **严格去重**：本次返回不与用户 7 天内已看内容重复（游客为一次持续访问内不重复）
- **新内容优先**：新上架内容在同档位内优先曝光
- **生产安全**：内容池 30 分钟全量刷新，原子切换零空窗
- **故障兜底**：Redis 异常自动降级到原 MySQL 直查，服务不中断

---

## 二、核心设计

### 1. 档位划分

视频质量用 `feed_weight` 字段（1~5）表示，**每个视频只属于一个档位**，直接映射：

| 档位 | 质量 |
|------|------|
| level 1 ~ 5 | 由 `feed_weight` 决定，5 为最高质量 |

### 2. Redis 存储结构

| Key | 类型 | 说明 |
|-----|------|------|
| `content:level:{1..5}` | Set | 各档位全量视频 ID |
| `content:level:{1..5}:new` | Set | 各档位新内容（3 天内上架），优先曝光 |
| `content:level:{1..5}:_shadow` | Set | 影子 key，供 30 分钟重建 |
| `content:level:{1..5}:_shadow:new` | Set | 新内容影子 key |
| `user:seen:{userId}` | ZSet | 登录用户 7 天已看记录（score=时间戳） |
| `user:seen:guest:{sessionId}` | ZSet | 游客一次持续访问内已看记录（短 TTL 自动过期） |

### 3. 每条推荐的主体流程

```
一次下拉 = 20 条
├── 按橄榄型比例逐档抽样（默认 level1~5 = 2/3/5/6/4，可由配置调整）
│    ├── 新内容优先（不足由存量补）
│    └── 动态扩采 + 已看去重
├── 若不足 20 条 → 全局补位（高质量优先 5→1）
├── 仍不足 → 兜底回放（全网已看完时，放开已看去重回 20 条，单次响应内不重复）
└── 最终按「体验曲线模板」编排下发顺序（高质开场、主体承接、避免单调递减、收尾钩子）
```

---

## 三、分档位采样算法（单档核心）

每档的目标是按橄榄型比例拿到对应条数（默认 2/3/5/6/4，合计 20）的**未看过**视频，例如档 4 抽 6 条、档 1 只抽 2 条。算法要点：

```
每档最多重试 3 轮
第 1 轮：随机采样 12 条候选
第 2 轮：随机采样 24 条候选（动态扩采）
第 3 轮：随机采样 36 条候选（上限 60）
每轮：
  1. 剔除「本次请求已选过」的视频（内存去重）
  2. 剔除「用户已看过」的视频（Redis 批量判断）
  3. 凑够该档目标条数即停
```

**为什么这样设计？**
- **动态扩采**解决了"档位内容多、未看数据少时随机抽不到"的核心痛点——重试次数越多采样越大，命中概率大幅提升。
- **本次请求内存去重**保证单次下拉内同档位绝不重复、跨档位也不重复。
- 重试上限 + 采样上限避免死循环和 Redis 压力。

---

## 四、去重与补位

### 去重策略
- **登录用户**：以 `user:seen:{userId}`（ZSet）记录 7 天内播放，到期自动剔除，避免无限膨胀。
- **游客**：以 `user:seen:guest:{sessionId}` 记录本次持续访问内已推荐内容，短 TTL（24 小时）自动过期，Redis 不会累积膨胀。
- 采用"**曝光即标记**"：推荐返回的视频即写入已看，刷过的下拉不会重复出现。

### 全局补位
当某档内容不足或未看不足其目标条数时，按**高质量优先（5→1）**顺序从能抽到的档位补充，保持总计 20 条，且沿用同样的去重/动态扩采逻辑，确保补进来的也尽量是高质量内容。

### 兜底回放
当全网未看内容不足 20 条（用户基本都看完了）时，**放开已看去重**从全量池回放旧内容补齐，并给前端返回 `is_rewind=true` 标记，保证**永不返回空列表**；同时**保留本次请求内去重**，避免同一条响应里出现重复视频（回放允许与历史请求重复，但不允许同一份 20 条内部重复）。

### 体验曲线编排
抽样/补位完成后，按「体验曲线模板」把 20 条重排成有节奏的顺序：开头保证 1~2 条高质量内容抓住用户、中段以 3/4 档为主体承接、整体避免单调递减、末尾尽量安排高质量或新内容作“钩子”。（模板以模块内常量的方式表达，属于静态可调项。）

## 五、内容池刷新（30 分钟）

采用**影子重建 + 原子 RENAME**，杜绝数据空窗：

```
每 30 分钟：
  1. 从 MySQL 拉取全部合格视频（按 feed_weight 归档到 5 档 + 新内容档）
  2. 校验每个视频可正常播放（排除内容非法的"空壳"）
  3. 写入 shadow key（分批 500 条，避免阻塞 Redis）
  4. 校验 shadow 非空（为空则放弃本次更新，保留旧数据）
  5. RENAME shadow → 主 key（原子切换，零空窗）
```

**为什么不用增量更新？**
升降档、下架、新增全部由全量重建自动处理，逻辑极简、无脏数据、无需 diff，且 30 分钟低频任务内存/流量压力完全可控。

**部署前提**：Redis 内容池全部建好并通过 SCARD 校验后才对外切流量。

---

## 六、故障降级

- Redis 正常时走推荐算法。
- Redis 不可用时，自动降级到**原有 MySQL 直查逻辑**，服务不中断、不报错。
- 通过配置开关 `feature_recommend_redis` 控制是否启用（默认关闭，可用于灰度发布）。

---

## 七、关键设计决策

| 问题 | 决策 | 理由 |
|------|------|------|
| 多次采样同档重复？ | 本次请求内存去重 | 简单可靠 |
| 档位抽取比例？ | 橄榄型（默认 2/3/5/6/4，可配置） | 中档为主、高档保量、低档少量，避免开头堆低质 |
| 20 条怎么排序？ | 体验曲线模板重排 | 高质开场、避免单调递减、尾部留钩子，兼顾留存 |
| 回放同响应重复？ | 保留本次请求内去重 | 回放允许跨请求重复，但同一份不重复 |
| 档位耗尽判断？ | 物理耗尽（空） / 逻辑耗尽（3 轮凑不够） | 区分处理不死循环 |
| 少量未看抽不到？ | 动态扩采 12→24→36 | 命中概率大幅提升 |
| 能否用 redis set 差集 SDIFF？ | 禁止 | 高 QPS 会打挂 Redis，改用多采+业务过滤 |
| 用户看完所有内容？ | 7 天窗口 + 兜底回放 | 永不无内容 |
| 30 分钟刷新会空窗？ | 影子 + 原子 RENAME | 0 空窗、0 事故 |
| 游客数据膨胀？ | 短 TTL + 独立命名空间 | Redis 不累积 |

## 八、可配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 每档均匀目标条数（旧 `recommend_per_level_target`） | 4 | 保留用于向后兼容，当前逻辑（默认为橄榄型）不再直接依赖它 |
| 每档分档目标条数（`recommend_per_level_counts`） | 空 → 默认橄榄型 `2,3,5,6,4` | 逗号分隔 level1~level5；显式配置可覆盖（如要均匀则配 `4,4,4,4,4`） |
| 总目标条数 | 20 | |
| 新视频窗口 | 3 天 | 新内容优先曝光 |
| 基础采样数 | 12 | 动态扩采基准 |
| 单档最大采样 | 60 | 单次上限 |
| 单档最大重试 | 3 | |
| 登录已看保留 | 7 天 | |
| 游客已看保留 | 24 小时 | TTL 自动过期 |
| 建池批次 | 500 条 | 避免阻塞 Redis |

说明：默认即橄榄型 `2/3/5/6/4`（低档少、中间档为主、高档精品保量）；如业务需要回到旧的完全均匀，可显式配置 `recommend_per_level_counts=4,4,4,4,4`。体验曲线模板当前以模块内常量形式提供，可按业务需要后续提升为配置项。

所有参数均可通过配置灵活调整，无需改代码。
